What it does

The connective tissue for multi-agent CLI orchestration.

Command-line tools — including the most capable AI coding agents — are islands. Each runs alone, each needs a human to drive it, and there is no native way to make two of them work together.

cli2cli-mcp changes the unit of work from "one CLI, one human" to "many CLIs, one program." Every tool becomes a persistent, addressable session. Read any session's output, write to any session's input, run as many as you want in parallel — the primitives that let a host or an orchestrator route work between Claude, Gemini, and shell as a single coordinated system.

It's key-free and local-first: the intelligence lives on the MCP host that connects to it; cli2cli-mcp holds no credentials and calls no model. It does one thing supremely well — make CLIs drivable and connectable — and is deliberately built to be orchestrated.

Before: isolated tools

  • Every CLI runs alone, blind to the others
  • A human has to sit and drive each one
  • No way to pipe one agent into another
  • One tool, one session, one task at a time

After: a coordinated fabric

How it works

Addressable sessions — an orchestrator routing between CLI agents

session A
claude · plan
⇒

Each box is a persistent PTY session with its own session_id. The host spawns them, reads each one's output, and writes the next directive — so A's result flows into B, B's into C. cli2cli-mcp provides the wiring; the routing logic lives on the host (or a thin orchestration layer above it).

Processes, not API calls — the wedge

Every agent framework today orchestrates model API calls. cli2cli-mcp orchestrates the real CLIs — the actual claude / gemini binaries and any shell tool, with full local files, credentials, and context, on a machine you own. That's a different and more defensible category: multi-agent orchestration at the process level, local-first.

Why a real pseudo-terminal

CLIs behave differently for a terminal than a pipe (colors, cursor control, prompts). cli2cli-mcp uses node-pty — Windows ConPTY — so agents run exactly as they would for a human and stdin injection actually reaches them. Sessions are held open and independently addressable, which is what makes cross-CLI coordination possible.

For daily users — AI practitioners
How to use it: register it once in your MCP host, then ask your assistant in plain language to spin up CLI agents, connect them, and drive them — it composes the five tools for you.

Step 1: register it

claude mcp add cli2cli -- node \
  C:/dev/cli2cli-mcp/dist/index.js

A Claude Code session then lists the cli2cli tools automatically. Works the same in Cursor / Claude Desktop via their MCP config.

Step 2: coordinate agents

-- say this to your assistant --
Spawn a gemini session to review this
design, then feed its notes into a
claude session to implement it.

Run the interactive db migration
and answer its prompts to apply it.

It spawns each session, routes output between them, and answers prompts — no babysitting.

Good to know

  • The assistant is the intelligence — cli2cli-mcp gives it the terminals and the wiring
  • Each agent is its own session; run and coordinate several at once
  • One agent's output can be read and written straight into another as a directive
  • It also answers wizards / (y/n) / menus that would otherwise block a tool
Developer & operator reference

Architecture — one server, one file

MCP host (Claude Code · Cursor · Desktop · a script)
      │  stdio (JSON-RPC / MCP)
      ▼
cli2cli-mcp  src/index.ts  →  dist/index.js      # the whole server, 5 tools
      │  node-pty (Windows ConPTY / POSIX)
      ▼
   any interactive CLI  (claude · gemini · shell · custom)

Runtime deps: @modelcontextprotocol/sdk, node-pty, uuid. Sessions are held in memory with bounded output buffers; env placeholders (e.g. a stray ANTHROPIC_API_KEY=your-api-key-here) are scrubbed before a child is spawned.

The five tools

ToolSignaturePurpose
spawn_cli_session({cli_type, initial_prompt?, working_dir?, command?, args?}) → {session_id}Launch a CLI in a PTY. cli_type: claude · gemini · shell · custom.
read_cli_stream({session_id}) → {output, is_waiting_for_input, is_exited, exit_code}Drain new output; flag an interactive pause or exit.
write_cli_input({session_id, input_text, append_newline?}) → {ok}Feed stdin — confirmations, answers, raw keystrokes.
list_cli_sessions() → {sessions[]}Every live session and its state.
terminate_cli_session({session_id}) → {ok}Kill a session and free its resources.
Presets are de-opinionated. The claude preset defaults to safe (--print, no auto-skip-permissions). Anything opinionated or autonomous is the caller's choice via cli_type:"custom" with explicit command + args — so the substrate stays generic.

Register (MCP config)

"mcpServers": {
  "cli2cli": {
    "command": "node",
    "args": ["C:/dev/cli2cli-mcp/dist/index.js"]
  }
}

Or one-liner: claude mcp add cli2cli -- node .../dist/index.js.

Build & verify

cd C:\dev\cli2cli-mcp
npm install       # node-pty prebuilt
npm run build     # tsc → dist/
node scripts/smoke.mjs   # PTY round-trip

Node ≥ 20. Smoke test needs no external CLI.

Notes & gotchas

ItemDetailHandling
ANSI in outputConPTY emits colors/cursor codes; results carry escape sequences.The caller strips them (the host session, or your wrapper).
Windows binary shimsclaude/gemini are .cmd shims; ConPTY needs the resolved path.Bare names are resolved via PATH/PATHEXT at spawn.
Multi-line via argvA newline in an argv passed through claude.cmd truncates.Feed long/multi-line prompts via stdin or a redirected file, not argv.
Interactive-prompt flagis_waiting_for_input is a regex heuristic.Treat it as a hint; the caller can always read + decide directly.
Placeholder env varsA dummy key in the environment can break a spawned CLI.The server scrubs obvious placeholders before spawning children.
